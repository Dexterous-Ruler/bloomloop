# BloomLoop

**An adaptive, Bloom's-taxonomy classroom and learning platform for Indian colleges.**

A professor uploads the deck they already teach. BloomLoop turns it into a question bank
in which every item is tagged to one of the six levels of Bloom's revised taxonomy. The
professor approves the questions, then runs a live room where **each student is served
questions at the level they have actually reached**, re-planned after every answer.

Between classes, students with an account practise in a **Learning Hub** built from the
same material. It offers prerequisites, adaptive practice, lessons, spaced review and
hints in English, Hindi and Marathi. Every answer from the room and the hub becomes
evidence that rolls up into course-outcome attainment reports that a college can file.

## What it does

### For the professor

| Area | What it does |
|---|---|
| **Material** | Upload a `.pptx` or paste syllabus text. Topics are read out, each with its slide range. Slide pictures are kept for use as figures. |
| **Question bank** | Questions are generated by the AI on the professor's button, or written by hand. Each is tagged to a Bloom level and cites its slides. Nothing reaches a student until the professor approves it. |
| **Question kinds** | 21 kinds. The original 16: multiple choice, true/false, multi-select, match, categorise, order, rank, fill in the blank, cloze, numeric, open (written), hot text, dropdown, table, grid and poll. Five interactive kinds on figures: tap a part, label a diagram, plot a point or line, mark a number line, set bar heights. |
| **Figures for every subject** | Graphs from fixed function families, charts, number lines, geometry and ray optics, timelines, flowcharts and trees (Graphviz), chemical structures (RDKit), patterns and call stacks. They are drawn as SVG on the server, each with a text description and a data table. A figure can step through on the projector. |
| **Live room** | A room code for phones; Student-devices, Teacher-led or Mixed. A live heat map by Bloom level, the student card, insights, and an AI "teaching move" suggestion that uses class aggregates only. There is also a fair wheel with think time, class questions with confidence voting and pause–discuss–re-vote, misconception tags on wrong options, and a projector page that shows no staff data. |
| **Class records** | Roster (CSV import), attendance, observations, tallies and activities. They are kept apart from marks and never move a level. |
| **Attainment and reporting** | Course outcomes mapped to topics. The attainment formula is set per college and versioned. The marks register, per-room and per-level comparisons, and CSV and printable reports all keep evidence types separate (digital, provisional machine-marked, human-reviewed, polls, re-votes). |
| **Learning Hub (staff side)** | Units and topics, prerequisite links (AI-proposed, professor-confirmed), and review queues for explanations, hints, lessons and translations. Each class and each student's progress is shown in roll order. |

### For the student in a room

The student joins with the room code and their roll number; no account is needed. They
answer on a phone and see a plain reason for what comes next, with an optional
"Sure / Think so / Guessing" tap. The phone keeps answers on the device when the network
drops and sends them on reconnecting.

### For the student in the Learning Hub (account required)

- **Mastery map:** units and topics, each with its state and the number of answers behind
  it.
- **Get Ready:** a short check across a topic's prerequisites, followed by a refresher path
  that says why each step is on it.
- **Practice and review:** adaptive practice with feedback after each attempt, spaced
  review, and an automatic error log.
- **Self-tests:** no feedback until submit.
- **Lessons:** built from the professor's slides, with worked examples and a concept panel.
- **Language:** a switch between English, हिन्दी and मराठी. A translation shows only once
  the professor has approved it.
- **Hints:** a ladder of hints that stops short of the answer. There is no live chat.
- **Progress:** goals, and Bloom levels compared with the student's own last month. There
  are no ranks.

### For the head of department

Read-only views of the department's classes, reports and hubs.

## How it decides

### The room ladder

The ladder lives in [`server/src/services/mastery.js`](server/src/services/mastery.js) and
[`selector.js`](server/src/services/selector.js) as pure functions, so it can be unit-tested
and explained in a sentence.

- A student with no history starts at **Understand**.
- Over the last **5** answers at the current level, with at least **3**:
  - **70% or more promotes** one level;
  - **below 40% demotes** one level.
- A student below **40%** overall, after at least 3 answers, is served **Remember and
  Understand only**.
- The mastery goal is a room setting, **80%** by default.
- Every move stores its reason and the number of answers behind it.
  - **Staff** see the full sentence.
  - **The phone** gets a neutral sentence that never names a band.
- **The live loop makes no AI call.** Generation happens before class, on the professor's
  button.

### The Learning Hub

- **Mastery:**
  - an Elo rating per student per topic, and per question;
  - item ratings are seeded from the Bloom level, with an uncertainty-based K (Pelánek,
    2016);
  - a topic is Mastered at an estimated 80% with at least 5 answers;
  - with fewer than 3 answers it is "Not sure yet".
- **Spaced review:** [`ts-fsrs`](https://github.com/open-spaced-repetition/ts-fsrs) with
  default parameters, one card per student per topic.
- **Get Ready:** at most 12 questions over a topic's confirmed prerequisites, nearest
  first. It stops early once the evidence suffices.
- **Closed questions:** a question that is live in a room, on an open self-test or in a
  running Get Ready check is closed to practice. Its key cannot be fetched before it is
  asked.
- **Serve tokens:** practice and lesson answers count only for questions that practice
  actually served to that account (a signed serve token).

### Attainment

- **The formula is data:** thresholds, attempt mode, room weights and the evidence types
  counted. It is versioned, and every report names the formula, its version and the
  methodology.
- **Not counted by default:** provisional machine marks, re-votes and teacher records.
- **A human review replaces a machine mark.**
- **Never counted:** confidence taps.

### Offline

- **The outbox:** every answer goes into an IndexedDB outbox first and is replayed in
  order. The answer id is the idempotency key, so a replay never makes a second row.
- **Question packs:** a phone may take a small pack of approved questions with **no answer
  keys**. It works through them offline; the server marks the answers in arrival order and
  never trusts the device's clock.
- **Late answers:**
  - an answer that arrives within **10 minutes** of a room closing still counts;
  - later ones are kept and marked as not counted;
  - at most 100 such kept answers per student per room.
- **Teacher records** carry an idempotency key, so an offline console can replay them
  safely. A stale write is refused, with what is newer.

### AI, and where it is not used

- **Generation:** Gemini writes questions, explanations, hints, lessons, translations,
  prerequisite proposals and teaching moves.
- **When:** only on a professor's button, asynchronously.
- **Source:** only from the professor's own material, citing the slides.
- **Approval:** everything arrives as an **AI draft** until the professor approves it.
- **Figures:** drawn by code from data, **never** by an image model.
- **Maps:** not generated. Indian law on map boundaries needs a lawyer's view first.

## Principles

These are rules in the code, not just in the UI.

- **Nothing that ranks a student:** no leaderboards, coins, streaks, class averages shown
  to a student, or labels like "slow learner" anywhere a student can see. Staff lists are
  in roll order by default.
- **Evidence is append-only:** every response is stored, including late answers, re-votes
  and replays. Nothing is overwritten or discarded.
- **Keys stay on the server:** no answer key reaches a phone or the projector before the
  attempt (or the reveal). The phone never holds keys, even offline.
- **Access is checked on the server:**
  - "not yours" and "not there" return the same 404;
  - a head of department reads and never writes;
  - a phone never reaches a staff route.
- **Honest numbers:**
  - every estimate carries the number of answers behind it;
  - provisional states are marked;
  - AI drafts are labelled;
  - a warning flags when translation may have changed a question's difficulty.
- **Under-18 mark:** a student marked under 18 on the roster has integrity signals
  neither recorded nor shown. This is a working posture; a lawyer must confirm it.

## Quickstart

Node 20 or newer (the Docker image uses Node 20), and npm workspaces.

```bash
npm install
```

```bash
cp .env.example server/.env
```

```bash
cp client/.env.example client/.env
```

Every key is optional; see [Running without keys](#running-without-keys).

### Supabase (one time)

1. Create a project at [supabase.com](https://supabase.com).
2. In the SQL editor, run every file in [`supabase/migrations/`](supabase/migrations/) in
   number order, `0000` to `0036`. Each is idempotent and additive. See
   [`supabase/README.md`](supabase/README.md) for what each adds, and which ones rooms need.
3. Copy the project URL into `SUPABASE_URL`. Copy the **service-role** key into
   `SUPABASE_SERVICE_ROLE_KEY` in `server/.env` only.
4. Copy the anon (publishable) key into `VITE_SUPABASE_ANON_KEY` in `client/.env`.
   This one is public by design.

Row level security is **on with no policies**, so only the server's service-role key can
read or write. Accounts (professor, HOD, student) use Supabase Auth and are invite-only.

> `@supabase/supabase-js` is pinned to exactly `2.45.4`. Newer releases need a native
> `WebSocket` (Node 22+), and on Node 20 they fail at connect. The server would then fall
> back to its in-process store and quietly run without persistence. Keep the pin, or move
> the whole project to Node 22.

### Run it

Development, with two processes and hot reload (API on `:5050`, client on `:5173`):

```bash
npm run dev
```

Demo, with the client built and everything served from one origin on one port, which is
what phones on a hotspot need. The server prints the LAN address students type, ending in
`/join`:

```bash
npm run demo
```

A seeded room with one student in the below-40% band and one at the top of the ladder:

```bash
npm run seed
```

| Who | Where |
|---|---|
| Professor console | `/` (sign in, or `/?key=<TEACHER_KEY>` with the shared key) |
| Students in a room | `/join` |
| Students' Learning Hub | `/hub` (student account) |
| Staff view of the hub | `/hubs` |
| Projector | `/wall`, opened from the console as a link with its own token; it holds no credentials |

## Configuration

`server/.env` (see [`.env.example`](.env.example)):

| Setting | Purpose |
|---|---|
| `GEMINI_API_KEY`, `GEMINI_MODEL` | Question, explanation, hint, lesson and translation drafts. Without them, a deterministic offline template writer is used, and its output is labelled. |
| `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` | The primary store and accounts. The service-role key is server-only. |
| `MONGO_URI` | Optional second store, tried if Supabase is unset or unreachable. |
| `TEACHER_KEY` | Shared key for the professor console without accounts. If blank, a new one is generated at each boot. |
| `SERVER_SECRET` | Signs hub serve tokens and the tokens of tap and label questions. **Set it once per deployment and keep it.** |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | Optional Google Classroom posting. |
| `PORT`, `CORS_ORIGINS` | The port, and any extra origins allowed to call the API. |
| `LAPTOP_ARCHIVE_DIR`, `LAPTOP_ARCHIVE_SECONDS` | Laptop mode: where rooms are saved while they run, and how often. |

`client/.env` (see [`client/.env.example`](client/.env.example)):

| Setting | Purpose |
|---|---|
| `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` | Sign-in for accounts. Public by design; **never** put the service-role key here. |

## Running without keys

The server says which mode it is in at boot, on `/api/health`, and in the console's top
bar.

| Missing | What happens |
|---|---|
| `GEMINI_API_KEY` | Questions come from a deterministic offline template writer, labelled as such. Explanations, hints, lessons and translations are not generated; the professor can still write them by hand. |
| `SUPABASE_*` | Falls through to `MONGO_URI`, then to an in-process store: everything works for rooms, and nothing survives a restart. Accounts and the Learning Hub need Supabase. A Supabase that is configured but missing a migration is named at boot. |
| `GOOGLE_*` | CSV export only. The Classroom button explains why it is disabled. |

## A classroom with no internet

```bash
npm --workspace server run laptop
```

This runs the same server on the professor's laptop, for phones on its hotspot or a travel
router.

- **Teacher key:** it refuses a key shorter than 16 characters.
- **Saving:** it saves each room to a local folder while the room runs, writing complete
  files only.
- **Back online:** the room files are imported to the cloud deployment, once each, never
  overwriting anything.
- **Not available in this mode:** sign-in, the Learning Hub and AI generation.

The step-by-step guide is [docs/TRAVEL_ROUTER.md](docs/TRAVEL_ROUTER.md). The trade-offs of
questions held on a phone are in [docs/OFFLINE_SELECTION.md](docs/OFFLINE_SELECTION.md).

## Testing

Every suite runs **offline**: on the in-process store, or on PGlite for the migrations. No
suite touches Supabase, Mongo or Gemini.

```bash
bash scripts/test-offline.sh
```

It blanks the network settings in the environment first (dotenv never overrides a variable
that is already set), then runs:

- **Unit tests:** about 1,280 tests, with `node --test`.
- **Migration test:** builds every migration on PGlite, re-runs it over data and upgrades
  older databases.
- **35 end-to-end scripts:** each starts its own server on a random port and drives real
  sockets and HTTP. Among them:
  - the live loop and security;
  - evidence and review;
  - kinds and media;
  - roster, records and modes;
  - insights, outcomes, attainment and the Phase 4 acceptance run;
  - class questions, misconceptions, honesty and key safety;
  - the Learning Hub (`hub`, `practice`, `paths`, `lessons`, `tutor`);
  - offline (`offline`, `laptop`, `recordsync`);
  - figures (`figures`, `figkinds`);
  - the design-zip gaps (`zipgaps1`, `zipgaps2`).

Each suite's output goes to `.test-output/`, with a summary of exit codes.

To run one script by hand:

```bash
SUPABASE_URL= SUPABASE_SERVICE_ROLE_KEY= SUPABASE_ANON_KEY= MONGO_URI= GEMINI_API_KEY= node server/scripts/hub.mjs
```

> `npm run smoke` (`server/scripts/smoke.mjs`) is the one script written for **live** keys.
> Run it only on purpose, since it can use Gemini quota.

What each suite proves, and its latest figures, are in [docs/TESTING.md](docs/TESTING.md).

## Deploying

1. Apply every migration, `0000` to `0036`, in number order, **before** deploying the new
   server. Rooms need `0022`, `0023`, `0024` and `0030`: without them, the boot probe stops
   using Supabase and names the missing file.
2. Set the server's secrets as environment variables: `SUPABASE_*`, `GEMINI_*`,
   `TEACHER_KEY` and `SERVER_SECRET`. `.dockerignore` excludes every `.env`.
3. Build from the [`Dockerfile`](Dockerfile): Node 20, the client compiled at build time,
   and only the server's runtime dependencies in the final image.

The hosted demo (Koyeb, eco-micro, Singapore) runs an **earlier build**. This branch has
not been deployed.

## Architecture

```
 phones (/join, /hub)          Node + Express + Socket.io                Supabase Postgres
 professor console ──REST──▶  routes ─ services ─ repo interface ───▶   (RLS on, no policies)
 projector (/wall)  ──socket─▶ live room loop (no AI calls)        ┌──▶  MongoDB  (fallback)
                               figure engines (SVG, server-side)   └──▶  in-process (fallback)
                               rich text (MathML, highlighted code)
                                   │  professor's button only
                                   ▼
                               Gemini (structured output, drafts)
```

- **Storage:** the store sits behind one repository interface with three implementations
  (Supabase, MongoDB, in-process). They have the same methods, and a parity test enforces
  that.
- **Rendering:** formulas (with chemistry) become MathML through
  [temml](https://temml.org). Code is highlighted with [shiki](https://shiki.style). Both
  run on the server, so the phone runs no rendering code.
- **Figures:** Graphviz and RDKit run as WebAssembly on the server.
- **Contracts:** the API and socket contract is in [`CONTRACT.md`](CONTRACT.md) and
  [`V2-CONTRACT.md`](V2-CONTRACT.md); amendments are dated.

## Status and known limits

The roadmap's Phases 0–7 are built, along with figures for every subject, the interactive
kinds and the design-zip gaps. Every suite passes offline.

**Never run against:**
- a hosted Supabase project, real Supabase Auth sign-ins, MongoDB or real Gemini output;
- a real phone or iOS, or a screen reader;
- MathML on a low-end Android device;
- two server processes.

**Not built:**
- erasure of archived rooms for DPDP;
- a live chat tutor (an owner option; it conflicts with the "AI only on the professor's
  button" rule);
- adaptive paper cards;
- generated maps.

**Legal:**
- The under-18 handling and the DPDP posture are working defaults. A lawyer must confirm
  them before any college signs on.
- The same goes for any map of India.

The full list is in [docs/IMPLEMENTATION_STATUS.md](docs/IMPLEMENTATION_STATUS.md) and the
latest session report in [reports/](reports/).
